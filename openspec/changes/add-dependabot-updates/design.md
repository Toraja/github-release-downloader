## Context

See `proposal.md` for motivation. The repository is public and hosted on GitHub, with one Cargo package, a committed `Cargo.lock`, GitHub Actions workflows, and a local composite action. The `Test` workflow handles both pushes to `main` and pull requests targeting `main`, but its shared path filter excludes Cargo manifests and lockfiles.

The repository has no branch protection or rulesets. Native auto-merge therefore has no required status check to gate a merge. The `cargo-dist` version is an arbitrary value in `dist-workspace.toml` and is repeated in an autogenerated release workflow; neither value belongs to a Dependabot package ecosystem.

## Goals / Non-Goals

**Goals:**

- Use GitHub-hosted Dependabot without additional accounts, credentials, runners, or services.
- Keep Cargo dependencies, the lockfile, and GitHub Actions references current.
- Delay routine dependency adoption to provide time for malicious or defective releases to be detected.
- Use immutable commit references for external GitHub Actions in manually maintained files while retaining automated updates.
- Bound routine pull-request volume and keep failures attributable to one ecosystem.
- Validate every pull request targeting `main` with the existing Rust test suite.
- Automatically squash-merge patch and minor Dependabot updates only after the required test check passes.

**Non-Goals:**

- Automatically update `cargo-dist`, patch its generated release workflow independently, or regenerate that workflow.
- Automatically merge major dependency updates.
- Require the release workflow to pass before Dependabot auto-merge.
- Add a second dependency updater, a separate vulnerability scanner, or approval automation.
- Change runtime behavior or dependency version constraints solely to accommodate Dependabot.

## Decisions

### Use one Dependabot configuration with two ecosystems

Add `.github/dependabot.yml` with separate entries for `cargo` and `github-actions`, both rooted at `/`. This uses native managers for the repository's supported dependency sources and keeps update policy in GitHub's standard configuration file.

Alternatives considered:

- Hosted Renovate covers arbitrary version declarations but requires a third-party installation and has a larger configuration surface.
- Updatecli can update arbitrary files but requires a scheduled workflow, authentication, and maintenance of the updater itself.
- Combining tools would improve `cargo-dist` coverage at the cost of overlapping ownership and more operational work.

### Run weekly and group compatible updates by ecosystem

Schedule both ecosystems weekly. Create one patch/minor group for Cargo and one patch/minor group for GitHub Actions. Major updates remain separate pull requests and require manual review.

Separate ecosystem groups preserve useful failure isolation: a Rust dependency failure is not mixed with a CI action failure. Weekly batching limits notification and CI noise for this small repository. A group containing a major update cannot accidentally become eligible for automerge because major updates are excluded from the compatible-update groups.

Apply a seven-day cooldown to routine version updates in both ecosystems. Combined with a weekly schedule, a release will normally be proposed approximately 7-14 days after publication. Dependabot security updates are not subject to version-update cooldowns, so known vulnerabilities can still receive immediate pull requests and must pass the same required test check before merging.

Alternatives considered:

- Individual pull requests maximize isolation but create unnecessary volume.
- A single cross-ecosystem group minimizes volume further but makes failures harder to diagnose.
- Grouping major updates with compatible updates could prevent otherwise safe updates from being merged or broaden automerge risk.
- Daily updates provide little benefit for this release cadence and increase churn.
- Dependabot's three-day default cooldown reduces delay but provides a shorter observation period than desired for automatically merged updates.
- A fourteen-day cooldown provides more observation time but unnecessarily delays routine fixes for this repository.

### Pin external GitHub Actions to immutable commits

Replace external action tag references in manually maintained workflows and composite actions with full-length commit SHAs and retain a same-line version comment for readability. This initial conversion is manual because hosted Dependabot cannot currently be assumed to convert tag references to SHA pins. After conversion, Dependabot's GitHub Actions ecosystem maintains existing SHA references and their version comments when newer releases are available.

Local actions such as `./.github/actions/rust-test` are not external dependencies and remain unpinned. The seven-day cooldown applies when Dependabot selects newer GitHub Actions releases.

Alternatives considered:

- Floating tags are easier to read but can be moved after review, so they are not immutable supply-chain references.
- Renovate can explicitly convert action tags to SHAs, but introducing another updater conflicts with the low-management objective.
- A repository policy that requires SHA-pinned actions is incompatible with cargo-dist's generated tag references and is therefore outside this design.

### Preserve existing Cargo version-range behavior

Allow Dependabot to update `Cargo.lock` and change manifest constraints when an update requires moving beyond the declared compatible range. Do not pin the existing broad major-version constraints or introduce a new versioning policy as part of this tooling change.

Alternatives considered:

- Lockfile-only updates would reduce manifest changes but prevent Dependabot from proposing future major crate upgrades.
- Pinning exact crate versions would be a separate dependency-policy decision and would increase manifest churn.

### Run the test workflow on every pull request targeting main

Separate the workflow triggers instead of sharing one anchored condition. Keep path filtering for pushes to `main`, expanding it to include `Cargo.toml` and `Cargo.lock`, but remove path filtering from pull requests targeting `main`.

Running every pull request is necessary because a required workflow skipped by a path filter remains pending and blocks merging. It also avoids maintaining a growing list of files whose changes might affect validation. The existing composite action continues to provide formatting, Clippy, tests with coverage, and documentation checks.

Alternatives considered:

- Adding only Cargo files to the shared path filter would validate current Dependabot updates but could leave future required checks pending for unrelated pull requests.
- Removing all path filters would also run the suite for every push-side documentation or planning change, adding unnecessary CI usage.
- A dedicated dependency-validation workflow would duplicate the existing test workflow.

### Gate native auto-merge with repository protection

Enable the repository's native auto-merge setting and protect `main` with the `Test` job as a required status check. Do not require a human approval, because eligible Dependabot updates are intentionally unattended. Other existing checks, including the release workflow, remain visible but do not gate automerge.

This repository setting is part of the change even though it is not represented in a committed file. It makes CI enforcement independent of the automerge workflow and prevents merging an eligible update before validation completes.

Alternatives considered:

- A workflow that merges directly after observing a successful run would duplicate status-gating logic and make the safety rule less visible in repository settings.
- Requiring the release workflow would delay or block routine dependency updates for release-packaging concerns that the selected policy explicitly excludes.
- Leaving `main` unprotected would allow native auto-merge to merge without a required CI gate.

### Enable auto-merge only for verified patch and minor Dependabot updates

Add a workflow triggered by `pull_request_target`, limited to pull requests authored by `dependabot[bot]`. It uses `dependabot/fetch-metadata` to verify Dependabot ownership and determine the highest update type, then invokes `gh pr merge --auto --squash` only for patch and minor updates.

The metadata action must be pinned to a full commit SHA with a version comment. The workflow receives only `contents: write` and `pull-requests: write`, does not check out the pull-request branch, and does not execute pull-request-controlled code. GitHub's native auto-merge waits for the required `Test` check and disables itself if an unauthorized actor changes the Dependabot branch.

Alternatives considered:

- Running merge automation on `pull_request` gives Dependabot-originated workflows a read-only token and cannot enable auto-merge.
- Automatically approving PRs adds no value when repository protection does not require reviews.
- Automerging major updates accepts API and behavior changes that passing tests may not detect.
- Merge commits retain unnecessary bot-update history; squash merge keeps one dependency update per mainline commit.

### Give cargo-dist exclusive ownership of the generated release workflow

Exclude `.github/workflows/release.yml` from routine Dependabot GitHub Actions version updates. Cargo-dist treats this file as generated output and checks whether it matches its configured template, so allowing Dependabot to patch it would create competing owners and changes that regeneration can overwrite.

Do not add custom scripts or a second updater for `cargo-dist-version`. Updating cargo-dist remains a deliberate operation that includes reviewing its release notes, changing `cargo-dist-version`, and regenerating `.github/workflows/release.yml`. Allow cargo-dist to emit its normal action tags rather than maintaining a manual `github-action-commits` SHA map that would become stale between cargo-dist upgrades.

Review cargo-dist at least quarterly and sooner when a relevant security advisory is published. Dependabot `exclude-paths` affects routine version updates, not security updates; any security update proposed against the generated workflow must not be automerged and should normally be resolved by upgrading cargo-dist and regenerating its workflow.

Alternatives considered:

- Allowing Dependabot to update the generated workflow reduces action-version staleness but creates drift from cargo-dist's source of truth and may be overwritten or rejected during regeneration.
- Maintaining cargo-dist's `github-action-commits` map provides immutable references but creates a second manual update burden and allows those SHAs to become stale.
- Setting cargo-dist's `allow-dirty = ["ci"]` permits external ownership of the generated workflow but gives up cargo-dist's update and consistency guarantees.
- Leaving cargo-dist maintenance entirely ad hoc increases the chance that both cargo-dist and its generated action references become stale; a lightweight quarterly review retains single ownership without adding another updater.

## Risks / Trade-offs

- [Grouped updates can obscure which dependency caused a Cargo failure] -> Inspect the grouped diff and split or temporarily ignore an update when diagnosis is needed.
- [Tests may not detect semantic regressions in compatible updates] -> Restrict automerge to patch/minor updates and retain manual review for majors.
- [Running tests on every pull request increases CI usage] -> Keep push-side path filters; GitHub Actions is free for this public repository.
- [`pull_request_target` has elevated permissions] -> Pin the metadata action, restrict the actor and repository, grant minimal permissions, and never check out or execute PR content.
- [The seven-day cooldown and weekly schedule delay routine releases by up to approximately fourteen days] -> Accept the delay as supply-chain risk reduction; Dependabot security updates bypass the cooldown.
- [A SHA-pinned action without a release-associated tag may not receive normal semantic version updates] -> Keep a version or source-ref comment and review the first Dependabot updates for non-semantic action refs.
- [The generated release workflow uses movable action tags and its actions can age between cargo-dist upgrades] -> Preserve cargo-dist ownership, review cargo-dist quarterly, and respond earlier to relevant security advisories.
- [A security update may still target an excluded generated workflow] -> Do not automerge it; upgrade cargo-dist and regenerate the workflow, or review any emergency patch manually.
- [The required check name can drift if the job is renamed] -> Treat repository protection and the `Test` job name as coupled configuration and verify the rule after workflow changes.
- [Repository settings are not fully captured by the Git history] -> Record and verify the required setting as an implementation task.
- [`cargo-dist` can become stale] -> Keep it outside the automation boundary explicitly and update it during release-tool maintenance.

## Migration Plan

1. Change the test workflow triggers so every pull request targeting `main` runs `Test`, while relevant pushes to `main` remain path-filtered.
2. Convert external GitHub Actions references in manually maintained files to full-length commit SHAs with readable version comments.
3. Regenerate `.github/workflows/release.yml` through cargo-dist using its normal action tags and without a manual action-commit map.
4. Add and validate Dependabot configuration for weekly grouped Cargo and GitHub Actions updates with a seven-day cooldown and routine exclusion of `.github/workflows/release.yml`.
5. Add the narrowly scoped workflow that enables squash auto-merge for verified patch/minor Dependabot updates.
6. Enable native repository auto-merge and configure `main` to require the `Test` status check.
7. Review the first generated pull requests to confirm the release-workflow exclusion, cooldown, SHA maintenance, grouping, metadata classification, required-check execution, and automerge behavior.
8. Roll back by disabling native auto-merge and removing the automerge workflow; Dependabot updates can continue as manually merged PRs. Remove the Dependabot configuration as well if automated update PRs are no longer wanted.
